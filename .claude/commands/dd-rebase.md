# /dd-rebase - 处理分支合并冲突

当分支合并遇到文档冲突时，帮助重新应用变更意图。

## 用法

```
/dd-rebase <CR-id>
```

## 使用场景

```
主线: feature-x.md v1
分支A: CR-001 修改 feature-x.md → 已合并
分支B: CR-002 修改 feature-x.md → 需要rebase
```

当分支B尝试合并时，发现 feature-x.md 已被分支A修改，产生冲突。

## 执行步骤

1. **加载变更记录**
   - `changes/{CR-id}.md`
   - 提取原始需求和变更意图

2. **加载当前主线文档**
   - 涉及的 `features/{feature}.md`（已含其他分支的改动）

3. **意图提取**

   按优先级提取变更意图：
   1. **原始输入** - 人类最初的需求描述（最高优先级）
   2. **变更内容** - AI整理后的格式化内容
   3. **澄清记录** - 多轮澄清中的补充说明
   4. **feature.md差异** - 如果有历史版本，对比提取意图

4. **冲突分析**

   识别冲突类型：
   - **概念冲突** - 同一概念的不同定义
   - **指标冲突** - 数值/限制的不同设定
   - **顺序冲突** - 流程/步骤的不同排列
   - **范围冲突** - 功能边界的不同界定

   **输出分析报告**:
   ```
   === Rebase 分析: CR-{id} ===

   ## 变更意图
   {从原始输入提取的核心意图}

   ## 当前文档状态
   {主线文档的关键变化}

   ## 冲突点

   ### 1. {冲突描述}
   **类型**: 概念冲突 / 指标冲突 / 顺序冲突 / 范围冲突

   **变更想要**:
   {从CR提取的意图}

   **当前状态**:
   {主线文档的现状}

   **建议处理**:
   - 选项A: {描述}
   - 选项B: {描述}
   ```

5. **人类确认**
   - 人类review分析报告
   - 决定如何处理每个冲突
   - 可以选择建议选项或提供新方案

6. **重新生成文档**
   - 基于当前主线状态
   - 应用调整后的变更内容
   - 更新 CR 的"变更内容"章节（记录rebase调整）

7. **输出确认**
   ```
   Rebase 完成: CR-{id}

   处理的冲突:
   - {冲突1}: {选择的处理方式}
   - {冲突2}: {选择的处理方式}

   更新的文档:
   - features/{feature}.md
   - changes/{CR-id}.md (记录rebase调整)

   下一步:
   - review 更新后的文档
   - 继续 /dd-confirm 或 /dd-done 流程
   ```

## 核心理念

**重新应用变更意图，而非文本合并**

不是简单地合并两个版本的文档文本，而是：
1. 理解这个变更原本想做什么（意图提取）
2. 在新的上下文（已合并其他变更的主线）中
3. 重新实现这个意图（可能需要调整方式）

## 意图提取示例

**原始输入**: "登录支持手机号"
**变更内容**: "用户可以使用手机号+验证码登录"
**当前主线**: 已有邮箱登录，刚合并了微信登录

**提取的意图**: 增加手机号作为登录方式
**建议**: 在现有登录方式列表中添加手机号选项，与邮箱/微信并列

## 注意事项

- Rebase 后的 CR 保持原状态（draft/confirmed）
- 会在 CR 中添加 "Rebase记录" 章节记录调整历史
- 如果冲突无法自动解决，会明确标注需要人工决策
